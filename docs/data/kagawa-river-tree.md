# `kagawa_river_tree.json` の作成方法

生成スクリプト: [scripts/generate_river_tree.py](../../scripts/generate_river_tree.py)

## 目的

これまでの評価データセット（`toaruos_tree.json`, `git_tree.json`, `linux_kernel_tree_size.json` 等）はいずれも**ソフトウェアのディレクトリ階層**で、ディレクトリのサイズ（＝子ファイル・子ディレクトリのサイズの合計）が親ノードの値になる、という**加算的な構造**を持つ。この手法は「親ノードの変量をきっちり表そうとするとレイアウトが崩れる」ため、親の値が子の合計と一致しない・それぞれが独立した変量を持てるデータが必要だった。

異なるドメインの根付き木として、**河川の合流構造**（水系）を採用した。支流が合流して本流になるという構造はそのまま根付き木（河口を根とする）にでき、かつ「河川の区間ごとの長さ」という、子（支流）の値とは独立したスカラー量をノード高さにエンコードできる。

なお、ここでの「長さ」は瞬間的な流量（m³/s）ではなく、区間の物理的な長さ（m）である点に注意。W05データセット自体に流量属性が存在しないため長さを採用したが、結果的にこれは好都合だった。仮に流量を使っていた場合、質量保存則により本流の流量は上流各支流の流量の合計に近い値になりやすく、まさに今回避けたかった「子の合計＝親」の縮退を再発させていた可能性が高い。

### 合流点ベースの分割（重要な設計変更）

初期実装（公式の河川コード＝river_codeが変わる地点を境界にする方式）には、以下の問題があった:

日本の河川命名は「本流はどれだけ支流が合流しても改名しない、支流側だけが新しい名前を持つ」慣習になっている。土器川水系で実データを検証したところ、**土器川という1つの名前が、河口から源流付近まで25箇所もの支流合流を経ながら、ずっと同じ名前・同じriver_codeのまま続いていた**（26セグメント、合計34,009m）。そのためriver_code基準で木を作ると、土器川が「1ノードでheight=37,191」という、他の支流（最大でも1万強）から突出して大きい**分岐ノード**になってしまい、レイアウトアルゴリズム側で以下の連鎖的な問題を引き起こした（詳細は git 上のこの会話ログ / [docs/known-issues.md](../known-issues.md) 参照）:

1. 分岐ノード自身の高さが（現行のH_t予算圧縮の対象外のため）そのままレイアウトに反映され、極端に縦長になる
2. その子孫のダミーノードの`y_top`が押し上げられ、`B_d`（高さ予算）が極端に小さくなる
3. `B_d`が小さすぎて葉群のほぼ全ノードが「支配的ノード」化し、1行フル展開＋バラバラな幅拡張という縮退したレイアウトになる

対策として、**木の分割基準を「公式の河川名（river_code）」から「グラフ上の次数（トポロジー）」に変更した**。次数2のノード（セグメントが単に繋がっているだけ、公式名が変わる場合を含む）は区間を延長するだけで区切らず、**次数3以上のノード（＝複数の流れが物理的に合流する地点）でのみ区間を区切る**。この結果、土器川は25の区間（run）に分割され、最大でも11,157（元の37,191の約30%）まで縮小した。

```
分割前: 土器川 = 1ノード、height=37,191
分割後: 土器川由来の区間 = 25ノード、height合計=34,009（内訳は52〜11,157で分布、中央値818全体と近いオーダー）
```

分岐ノード自身の高さが局所的な合流点間距離に収まるようになったため、上記の連鎖的なレイアウト崩れは解消される。

## データソース

国土数値情報 河川データ（W05、shapefile形式）。

- 入手元: https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-W05.html
- 対象: 香川県（`PREF_CODE = "37"`）、土器川水系（水系域コード `880808`）
- スクリプトが `urllib` で該当県のzipを直接ダウンロードするため、手動での事前ダウンロードは不要（[generate_river_tree.py:64-102](../../scripts/generate_river_tree.py#L64-L102)）

W05データの中身は2種類のレイヤー:

| レイヤー | 型 | 使う属性 |
|---|---|---|
| `Stream`（河川中心線） | LineString | `W05_001`=水系域コード, `W05_002`=河川コード(10桁), `W05_004`=河川名, `W05_009`/`W05_010`=始点/終点ノードID |
| `RiverNode`（端点） | Point | `W05_000`=ノードID, `W05_011`=標高(m) |

## アルゴリズム

1. **フィルタ**: 対象水系コード（`TARGET_WATER_SYSTEMS`）に一致する`Stream`セグメントのみ抽出。
2. **実長の計算**: 各セグメントの折れ線をハーバサイン距離で積分し、メートル単位の長さを求める（`line_length`）。
3. **グラフ構築・次数計算**（`build_river_tree_by_confluence`）: 全ノードを頂点、全セグメントを辺とする無向グラフを作り、各ノードの次数（接続するセグメント数）を計算する。
4. **区間(run)の構築**: 連結成分ごとに標高最小のノードを河口（起点）とし、BFSで辿る。次数2のノード（通過点、公式名の変化点を含む）は区間を延長するだけで区切らず、**次数3以上のノード（物理的な合流点）でのみ区間を区切る**（`walk_run`）。1つの区間に複数の異なる公式名のセグメントが含まれる場合、代表名（`displayName`）はその区間内で最も合計長が長い名前を採用する（「名称不明」以外があればそちらを優先、`dominant_name`）。
5. **複数連結成分の合成**: 水系内に複数の連結成分がある場合、それぞれの河口側runを合成ルート（`ROOT_NAME`）直下の子として並べる。
   - 実際に土器川水系で検証したところ、この水系ではグラフは**連結成分1つ**にまとまっており、このロジックは今回のデータでは実行されていない（他の水系を対象にした場合に備えた一般化）。
   - もし複数連結成分が生じる場合、想定される原因は「同じ水系域コードの下に、独立して海に注ぐ複数の排水系統が行政上まとめられている」または「デジタイズ時のノード座標のズレによる本来繋がっているセグメントの分断」であり、「海まで繋がらない孤立河川」を意味するものではない。

「名称不明」セグメントも他と同様に、通過点なら区間を延長し、合流点なら区間として独立する（旧実装にあった「命名済み祖先への繰り込み」処理は、分割基準が名前ベースでなくなったため不要になり削除した）。河川等級（1級/準用河川など）による絞り込みは行っていない。

## 出力フォーマット

`src/App.jsx` が読み込む既存データセットと同じフラットJSON形式（`{name, parent, height}` の配列）。

```json
{
  "name": "<seg連番, 例: seg1>",
  "displayName": "<代表河川名>",
  "parent": "<親runのname、または合成ルート名>",
  "height": <区間の実長(m)、四捨五入、最小1>,
  "width": 1000
}
```

- `name` は区間(run)ごとの合成id（`seg1`, `seg2`, ...、生成順）。1つの公式河川名が複数の区間に分割されるため、`river_code`ではなく区間単位の連番をノード識別子にしている。表示名は`displayName`に分離。
- ルートノードは `ROOT_NAME`（"土器川水系"）、`height: 1`。

## 再生成方法

```bash
pip install pyshp
python3 scripts/generate_river_tree.py
```

`kagawa_river_tree.json` がリポジトリルートに上書きされる。対象水系や出力先を変えたい場合はスクリプト冒頭の定数（`PREF_CODE`, `TARGET_WATER_SYSTEMS`, `OUTPUT_PATH`, `ROOT_NAME`）を変更する。

## 既知の制約

- 標高最小ノード＝河口という前提について、土器川水系の実データで検証済み: 標高0mのノードは1個のみ・次数1（末端）で、ジオメトリ的にも河口らしい一意な点だった。BFSでホップ距離順に標高を追跡すると123エッジ中3件で局所的な非単調（1ホップ進んだのに標高が下がる）が見られたが、標高は連結成分ごとの起点選択のみに使われ木構造そのものには影響しないため、実害は確認されなかった。他水系・大規模水系では未検証。
- グラフに閉路（本来ありえないはずの合流→分流のループ等）がある場合、一部セグメントが`walk_run`のBFSから到達不能になりうる。その場合`generate_river_tree.py`実行時に`warning: N segments unreachable from any mouth`が標準エラーに出る（土器川水系では0件を確認済み）。
