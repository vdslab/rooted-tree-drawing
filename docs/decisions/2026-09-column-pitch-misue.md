# 列間の間隔を Misue 2024 の式と配線規約に合わせる

**ステータス: Implemented**（2026-09-14）

提案手法（SA / LPT / binpacking）のダミーノード内の列ピッチが、Misue 2024 の式(3)(5)より
`s_h` 広かった。論文に合わせて `w' = w + s_h` に縮めた。列間の表示ギャップは
`2·s_h`（実効600）から **`s_h`（実効300）** になり、既存手法の葉の間隔と一致した。

## 論文が定めている横方向の間隔

Misue 2024 は `w' = w + s_h`（葉の幅 + 水平間隔）と定義し、ダミー内の葉の相対位置を
次のように与えている（§4.3）。

| 場合 | 論文の式 | 列ピッチ |
|---|---|---|
| 1列 | `p_x(v_i) = s_h/2` | — |
| 1行・2列以上（式3） | `p_x(v_i) = i·w'` | `w'` |
| 2行以上・2列以上（式5） | `p_x(v_i) = s_h/2 + w'(i mod m)` | `w'` |

**どの場合も列ピッチは `w'`。** ダミー箱の幅は Table 1（左右マージン各 `s_h/2`）と
§4.5（van der Ploeg に渡す幅に `s_h` を足す補正）から `m·w' + s_h` になる。

実装は `core/dummy.js` が `(列数-1)·s_h` を追加計上し、`core/render.js` の列ピッチが
`w' + s_h` になっていたため、隣接する列の表示ギャップが `2·s_h` だった。既存手法
（`methods/existing.js`）は論文どおり `s_h` なので、面積効率 TNA/DA の比較で提案手法だけが
描画面積を余分に使っていた。

## 「列間にバス線が通るぶん広げるべきでは」への答え

提案手法は列ごとに縦のバス線を持つ。論文の式(3)(5)が想定する配置には列間にバス線が
通らない（§5.3.3 の折れ線では縦線はダミーの外縁に交互配置される）ので、
「Misue が行間で間隔を `2s_v` に倍化している（§4.3.3）のと同様に、横も倍化すべきではないか」
という疑問が立つ。

しかし**バス線まわりの余白をリード線の長さを単位に測ると、倍化は不要**だと分かる。

| | リード線 | バス線の片側のクリアランス | ギャップ合計 |
|---|---|---|---|
| Misue の行間バス（§4.3.3 + §5.1 Fig 7(a)） | `s_v` | `s_v` = リード線1本分 | `2s_v` |
| 提案手法の列間バス（採用） | `s_h/2` | `s_h/2` = リード線1本分 | `s_h` |

**「バス線はギャップの中央に置き、両側にリード線1本分の余白を取る」**という1つの規則で、
Misue の行間バスと提案手法の列間バスが同時に説明できる。論文が縦方向にだけ倍化して
見えるのは、水平リード線を `s_h/2`（垂直 `s_v` の半分）と定めているため（§5.1 Fig 7(b)）で、
単位を揃えれば矛盾しない。この規則を採ると列ピッチは `w'` となり、式(3)(5)とも一致する。

絶対値では列間バスの余白（`s_h/2`）が行間バスの余白（`s_v`）より小さいが、これは論文自身の
リード線の非対称（水平 `s_h/2` / 垂直 `s_v`）の帰結であって、規則からの逸脱ではない。

## 検討して却下した案

いずれもリード線 `s_h/2` は満たすが、バス線がギャップの中央に来ない。

| 案 | バス線の片側（異物 / 自分の列） | ギャップ | 却下の理由 |
|---|---|---|---|
| `1.5·s_h`（450） | `s_h` / `s_h/2` | `1.5 s_h` | 「異物クリアランスだけ `s_h` に揃える」という案。論文の縦バスの異物クリアランスを根拠にしたが、**それは設計された不変量ではない**（Misue 自身のレイアウトで実測すると隣が通常ノードか別ダミーの葉かで 150/300/450 とばらつく） |
| `2·s_h`（600、変更前の実装） | `1.5·s_h` / `s_h/2` | `2 s_h` | 「線が通るので倍」という読みは §4.3.3 に沿うが、バス線が中央から外れる。論文の行間バスは上下とも `s_v` で対称 |

## 変更箇所

幅の式と配置の式は対で直す必要がある（片方だけだとノードが重なる）。

- `core/dummy.js` の `calcDummyDataWidth`: `columnGaps` を落として `totalWidth + xMargin`
- `core/render.js` の `tx += colWidth + xMargin` 4箇所 → `tx += colWidth`
- `core/render.js` の `tx += colMaxWidths[i] + xMargin` 1箇所 → `tx += colMaxWidths[i]`

## 検証

- `test/golden.mjs`: 192ケース中121件のハッシュが変化。**重なりは全ケース0**、エラー0。
  既存手法の24ケースは不変（`methods/existing.js` はこの2ファイルを使わない）
- 葉12枚を積み上げた木で縦バス線の左右を実測し、**両側とも150**（= `s_h/2`）を確認
- `|V|=200` で隣接ノード対の最小水平ギャップが 450 → **300** となり、既存手法と一致
- `npm run build` 通過

## 影響

面積効率の実験値が変わる。論文・スライドの図は取り直しが必要。実測では提案手法が
全条件で +0.017〜+0.035（およそ +8%）改善し、既存手法は不変。
