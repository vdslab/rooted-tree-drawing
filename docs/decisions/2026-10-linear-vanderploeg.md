# van der Ploeg を論文どおりの線形時間アルゴリズムに置き換える

## 背景

`src/layout/core/tree.js` の `vanderploeg()` は、論文の考え方（左兄弟の右輪郭と、これから置く
部分木の左輪郭を比べて右へ押す）は同じだが、手順が論文と違い O(n) になっていない。

- 子1つごとに `d3.stratify` で木を作り直し、`descendants()` で部分木の全ノードから
  スカイラインを作り直している（O(n²) 前後）。
- 呼び出し側も `stratify(vanderploeg(root, stratify))` の形で、毎回 hierarchy を作り直している（6か所）。

論文: A. van der Ploeg, "Drawing non-layered tidy trees in linear time",
Software: Practice and Experience 44(12), 2014（[参考文献](../references/index.md)）。
付録 C の Java コードを正とする。

## 判断

van der Ploeg の部分全体を O(n) にする。外側の hierarchy の作り直しもやめ、
`vanderploeg(root)` が hierarchy の `data.x` / `data.y` を直接書き換える形にする。

**出力は変えない。** 論文付録 C の印のうち、本体（印なし）と非レイヤード拡張（⋆）だけを有効にし、
美的基準5のための拡張（◦ Buchheim らの中間兄弟の均等配置、• IYL による兄弟番号の参照）は
受け皿だけ作って無効にする。均等配置を有効にすると全手法の出力と実験値が変わるため、
実験の再取得とセットで別に判断する。

## 実装の順番

理論を1つずつ足し、各段階で「現行実装と同じ座標か」を `test/vanderploeg.test.mjs` で確かめる。
各段階を1コミットにし、すべて golden の変更なしで進める。

| Step | 内容 | 学ぶこと |
|---|---|---|
| 0 | 差分テストの土台（手書きの木・論文 §7 の生成法によるランダムな木・美的基準の検査） | 現行実装の性質 |
| 1 | y を先に確定、`prelim` / `mod` と `secondWalk`。輪郭はまだ素朴に全ノードから求める | 部分木の移動を `mod` で O(1) にする |
| 2 | `nextLeftContour` / `nextRightContour`、threads、極端ノード（`el` / `er`, `msel` / `mser`） | 線形時間の核心（論文 §4 の証明） |
| 3 | IYL、`moveSubtree(t, i, si, dist)`。`distributeExtra` / `addChildSpacing` はオプションで無効 | 均等配置の受け皿 |
| 4 | 呼び出し側を `root = vanderploeg(root)` に置き換え、実行時間の伸び方を測るテストを追加 | — |
| 5 | 旧実装の削除、文書の同期 | — |

新しい実装は `core/` に新設する vanderPloeg.js に置く。状態（prelim / mod / threads / IYL）が多く、

`growthIncremental.js` は部分木のキャッシュがスカイラインを前提にしているので、今回は対象外とし、
スカイラインはこの手法が使う間だけ残す。

## Step 0 で分かったこと

- **座標系は論文と同じ。** 現行実装は各ノードを「左端 0・上端 0」から始め、最初の子は動かさないので、
  最初の子だけをたどった先の葉の左端が 0 になる。論文の `prelim` の原点と一致するため、
  平行移動をそろえずに座標を比べられる。
- **親の x の決め方は論文と同じ。** 兄弟は上端の y が等しく左から重ならないよう並ぶため、
  「最も左に出ている子」と「最初の子」は一致する。論文 `positionRoot` と同じ値になる。
- **部分木は右にしか動かない。** 論文の `separate` は `dist > 0` のときだけ動かすので、
  最初から左兄弟より右にある部分木（根が広い子の中央に寄っている場合など）は原点に残り、
  左に隙間ができる。現行実装も同じ挙動で、ランダムな木300本のうち81か所で起きる。
  テストでは「左兄弟に接している、または動かされていない」を検査する。
- **IYL は線形時間のための部品ではない。** 「どの左兄弟の輪郭とぶつかったか」を求めるためのもので、
  使うのは均等配置（◦）だけ。線形時間を支えているのは threads と相対座標。
- 2026-09 に輪郭を「ノードの鎖」からスカイラインに変えた（[設計記録](2026-09-contour-skyline.md)）。
  原因は鎖の選び方の式の誤りで、鎖という表現そのものではない。threads による鎖は構造上正しい輪郭を
  たどるが、Step 2 では差分テストと重なりの検査で改めて確かめる。

## 結果（2026-11）

- `src/layout/core/vanderPloeg.js` に付録C を行単位で移植した（Step 1〜3）。呼び出し側6か所を
  `root = vanderPloegLayout(root)` に置き換え、`tree.js` の旧
  `vanderploeg` を削除した。スカイラインと兄弟探索は `growthIncremental.js` と `render.js` が使うので残した。
- **差分テストのオラクルを素朴な実装に替えた。** 旧実装を削除すると比較相手が無くなるため、
  仕様をそのまま書いた O(n²) の `naiveLayout` を `test/vanderploeg.test.mjs` に置いた。
  旧実装 = 素朴な実装（2,859本）、素朴な実装 = 線形時間実装（テストの459本に加え、深い木・高さが極端な木を含む
  2,400本）を確認してから旧実装を削除した。
- **golden の正規化を変えた。** ノードの座標は全630ケースで旧実装と一致した（差 1e-9 以下）が、
  エッジの座標が最下位桁だけ変わり（mod を足す順が変わったため。例: 397.5660673331979 → 397.566067333198）、
  エッジは丸めずにハッシュしていたので全ケースでハッシュが変わった。エッジもノードと同じく小数6桁で比べるよう
  `test/golden.mjs` を直し、**旧コードの作業ツリーで golden を作り直したうえで**新コードが630ケースすべて一致する
  ことを確かめた。golden.json の差分はハッシュのみ（ノード数・エッジ数・重なり数は不変）。
- 速度（van der Ploeg 単体、論文 §7 の生成法の木、最良値）:

  | ノード数 | 旧（スカイライン版） | 新（threads 版） |
  |---|---|---|
  | 250 | 4.0 ms | 0.22 ms |
  | 1,000 | 53 ms | 0.29 ms |
  | 4,000 | 1,362 ms | 0.57 ms |
  | 16,000 | — | 2.4 ms |

  パイプラインでは葉をダミーに畳んだ後の木（数十ノード）に対して呼ぶため、全体の短縮はこれより小さい。
- 均等配置（◦）は `vanderPloegLayout(root, { spacing: true })` で有効になる。論文 Figure 7 の形で
  挟まれた兄弟の間隔が揃うこと、有効にしても美的基準1〜3を満たすことをテストしている。有効化は未判断。
