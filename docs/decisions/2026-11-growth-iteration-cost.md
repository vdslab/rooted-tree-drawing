# 列成長型の1反復の計算量を減らし、2手法の違いを配置だけにする

## 背景

van der Ploeg の線形化（[設計記録](2026-10-linear-vanderploeg.md)）のあと、列成長型の1反復の計算量を
整理すると、差分更新版が差分になっていない部分が残っていた。

- 差分更新版は祖先ごとに部分木の全ノードの配置をコピーし、`stratify` とスカイラインを作り直していた。
  根の組み直しだけで折り畳み木の大きさ F に比例するので、線形の van der Ploeg より悪かった。
- `growth.js` は反復ごとに全ダミーの寸法を葉から計算し直していた（元の葉の数 N に比例）。
- 最底辺のダミーの探索とアスペクト比は、両手法とも F の全走査だった。
- `lptColumn` は呼ぶたびに全体をソートし、負荷最小の列を線形に探していた
  （冒頭コメントの O(n log k) と実装が合っていなかった）。

また、差分更新版はダミー化や正規化まで自前で持っており、`growth.js` との違いが配置以外にも散らばっていた。

## 判断

**2手法の違いは「全体を配置し直すか、差分だけ組み直すか」の1点だけにする。**

列成長のループを `growColumns`（`methods/growth.js`）に一本化し、配置だけを `placement` として差し替える。
`placement` は `aspectRatio()` / `update(target)` / `finish()` を持つ。パイプラインも `runLayout` を共有する。

理論的に減らせる所は、実装が複雑になっても減らす。

| 処理 | 以前 | 現在 |
|---|---|---|
| 最底辺のダミーの探索 | O(F) の全走査 | ヒープで O(log D)（両手法） |
| LPT | O(m log m + m k) | O(m log k)（両手法。初回と未ソート入力のみ O(m log m)） |
| ダミーの寸法の更新 | `growth.js` は O(N) | 対象だけ O(m)（両手法） |
| 配置 | 全体 O(F) / 差分は O(h F) 以上 | 全体 O(F) / 差分は経路上で並べ直す兄弟の数 × 輪郭の長さ |
| アスペクト比 | O(F) | 全体 O(F) / 差分は根の外枠から O(1) |

記号: N 元の葉の数、F 折り畳み木のノード数、D ダミー数、m 対象ダミーの葉の数、k その列数、h 対象の深さ。

## 成立に使う性質

- **ダミーの上端は固定。** ダミーは折り畳み木の葉で、祖先の寸法は変わらない。したがって変わるのは対象の
  下端だけで、更新する要素は常にヒープの先頭である。ヒープは先頭の更新だけを持ち、位置の管理を持たない。
- **LPT の入力の各列はすでに降順。** 前回の分配の各列は高さ降順に積まれている。列をマージすれば全体の
  ソートが要らない。高さの同点を番号の小さい列から出すと、列をつなげた安定ソートと同じ順になる。

## 差分の配置

部分木ごとに、輪郭（`{ x, bottom }` の配列）・外枠・子ごとのずらし量・子 0..j の森（prefix）をキャッシュする。
y は固定なので輪郭の y は絶対座標のまま持てる。子 i が変わったら親では prefix[i-1] から再開し、子 i 以降だけを
並べ直す。これを根まで繰り返す。全ノードの座標を書くのは停止後の `finish` の1回だけ。

`core/vanderPloeg.js` は流用していない。threads は親が子の部分木の中の葉を書き換える（`setLeftThread`）ので、
部分木を使い回すと以前の組み合わせの跡が残る。論文 §8.3 が状態を書き換えない実装に「輪郭を別のリストとして持つ」
ことを挙げているのと同じ理由で、Moen の動的な木の配置に近い形になっている。

**最悪計算量は改善していない。** 輪郭の配列をコピーするので、根の子が多く先頭の子が変わる木や、輪郭が
長い木では、1反復が F に比例しうる。改善するのは典型的な木の再計算量である。

## 検証

- `growth-lpt` と `growth-lpt-incremental` の出力一致（fixture 全件・golden）。
- 配置エンジン単体: ランダムな木900本で計36,000回葉の寸法を変え、毎回のアスペクト比と最終座標が全体の配置し直しと
  一致（相対誤差 6e-14 以下）。縮小版を `test/growth-incremental.test.mjs` に置いた。
- LPT: 素朴な LPT と分配が完全に一致（12万回の呼び出し。同点の多い入力・未ソート入力を含む）。
  `test/lpt-column.test.mjs` に置いた。
- golden は `growth` を含む全手法で不変。

## 実測

1000×750、UI余白、LPT、中央値（暖機3回＋9回測定）。開発環境での予備測定で、論文用の結果ではない。
「以前」は線形化前のコミット `eb25224`。入力は `src/App.jsx` と同じ変換をしたもの。

| 入力 | ノード数 | `growth-lpt` | 差分更新版 |
|---|---:|---:|---:|
| `inline-tree.json` | 1000 | 5.1 → 3.8 ms | 4.2 → 2.5 ms |
| `toaruos_tree.json` | 883 | 225 → 18 ms | 90 → 11 ms |
| ランダム（スケールフリー） | 3000 | 14.7 → 9.0 ms | 11.7 → 8.6 ms |

差分更新の利点は折り畳み木が大きい入力（`toaruos`）で出る。葉の多い木は折り畳むと小さくなり、差はほとんど出ない。

最初の実装のヒープは任意の要素の更新のために位置を `Map` で持っていて、LPT が理論上は速いのにランダムな木で
逆に遅くなった（12.5 → 16.1 ms）。更新するのは常に先頭だと分かったので `Map` をなくした。

## 残っていること

- `packing/lpt.js` は `lptColumn` とは別の LPT 実装を持つ（同点の割り方が違うので、統合すると `budget-lpt` の
  出力が変わる）。
- 実データの反復数の評価は `--metric=time` での取り直しが必要。
