# Grill Me

目的: ユーザーが提示した計画・設計・構成案を、代わりに書き直すのではなく、**対話**を通じて本人に強化させる。

## 対象の特定

会話中で直近に確定した計画・設計・構成案を対象とする。複数候補がある、あるいは指定された
ファイル/資料がある場合は、対象を1つに絞ってから始める。曖昧なら最初に一言で確認する。

## 質問する前に裏を取る

**効く質問は、事実を1つ握ってから出る。** 「懸念があります」で終わる質問は答えようがない。

計画がコードやデータに関わるなら、質問を作る前に読む・測る・実行する。そのうえで質問に
**具体的な数字やファイル名を埋め込む**:

- ✗「実験の再現性は大丈夫ですか？」
- ✓「`generateTree.js` は `Math.random()` を使っていてシード指定がありません。過去の結果は
   再現できませんが、それは許容ですか？」

この一手間がないと、以降のラウンドが全部「一般論への相槌」で終わる。

## 2種類の聞き方を使い分ける

| | 使う場面 | 手段 |
|---|---|---|
| **選択式** | 答えが列挙できる。判断を迫りたい。トレードオフを並べたい | `AskUserQuestion`（**1回に最大4問まとめて並列**） |
| **記述式** | 相手の言葉が欲しい。選択肢を出すと誘導になる。まだ選択肢が見えていない | 本文で普通に質問する |

**列挙できるものは全部まとめて並列で聞く。** 1問ずつ往復して相手を待たせない。
一方、「なぜそうしたいのか」「何を諦めてよいか」のように**答えが本人の中にしかないもの**は、
選択肢を作ると誘導になるので本文で聞く。1回のラウンドで両方混ぜてよい
（選択式4問 + 本文で記述式1問、など）。

### 選択肢の作り方

- 各選択肢の `description` には「それを選ぶと何が起きるか」を書く。判断材料が無いと選べない。
- 推す案があるなら**先頭**に置いて `(Recommended)` を付け、理由を description に書く。
  中立を装って黙るより、立場を示して反論してもらう方が早い。
- 「まだ決められない」「今は触らない」を選択肢に入れる。**保留も立派な判断**で、
  無理に決めさせると後で覆る。
- 排他でない選択肢は `multiSelect: true` にする。

### 投げる前に検査する

面接の途中でツール呼び出しが弾かれると対話が途切れる。ペイロードを検査してから投げる:

```bash
node .claude/skills/grill-me/check-questions.mjs questions.json
# または
echo '<json>' | node .claude/skills/grill-me/check-questions.mjs
```

```
✗ questions[0]: options は2〜4個（今は5個）。5個以上は弾かれるので統合するか質問を分ける
✗ questions[0]: header は12文字以内（"とても長いヘッダー文字列です" は14文字）
✗ questions[0]: options[1] に "Other" を自分で足さない（UIが自動で出す）
```

## 何を聞くか

観点は以下から選ぶ（毎回全部は使わない。対象にとって一番効くものを選ぶ）:

- **前提**: 検証されていない前提、確認していない事実は何か
- **優先順位**: 制約（時間・人手）下で最初に削るのはどこか。それを今決めているか
- **証拠**: 主張を裏付けるデータ・実測値は手元にあるか、希望的観測か
- **一貫性**: 持ち帰ってほしい結論と、各パートに割いている比重が合っているか
- **対象読者/目的**: 誰のための計画か。その相手に本当に必要な情報か
- **弱点の看過**: 都合よく見えて実は一番弱いところはどこか

質問は一般論にせず、計画の中の**具体的な箇所**（章番号、ファイル名、数値）を名指しする。

## 回答を受けたら

1. **含意を言語化する。** 「その答えなら、計画のここが変わる」を先に示す。表面的な追認で
   次に進まない。答えによって**前のラウンドの結論が覆る**こともあるので、その場合は
   何が変わったかを明示する（覆ったこと自体を咎めない。最新の判断を採る）。
2. **鵜呑みにしない。** 「削除でいい」と言われても、破壊的な操作の前には中身を確認する。
   確認した結果、前提が逆だったことが実際にある（「新しい方を残す」つもりが、
   残す予定のファイルの方が古かった）。
3. **次のラウンドへ。** 詰めるべき点が残っていれば、同じ要領でまた並列に聞く。

## 終わり方

ユーザーが「十分」と言うか、これ以上詰める点がなくなったら終了する。最後に:

- **更新後の計画**を簡潔にまとめる（何がどう変わったか）
- **未決のまま残った項目**を、なぜ決められなかったかと一緒に列挙する
  （保留は失敗ではない。次に何が分かれば決まるかを書く）

## トーン

- 敵対的にならない。厳しいが具体的で、答えられる質問にする。
- 「なんとなく気になる」ではなく、「なぜそれが問題になりうるか」を一言添える。
- ユーザーの労力を尊重する。答えにくい質問を連発して詰まらせるのではなく、
  答えることで計画が実際に良くなる質問を選ぶ。
- **質問数を絞ること自体は目的ではない。** 並列で聞けるものを小出しにする方が消耗させる。
